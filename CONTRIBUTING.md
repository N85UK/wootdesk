# Contributing to WootDesk

Thank you for your interest in contributing to WootDesk! We welcome pull requests, bug reports, and feature proposals.

---

## Development Workflow

1. **Prerequisites:**
   - macOS 15.0+ with Xcode 16.0 or later.
   - XcodeGen (`brew install xcodegen`).
   - Node.js 22 or later for the dependency-free push gateway checks.

2. **Branching Strategy:**
   - External contributors should branch from `main` using descriptive names:
     - `feat/feature-name`
     - `fix/bug-description`
     - `docs/documentation-update`
   - Submit contributor changes through a pull request. Maintainers may work
     directly on `main` only when the repository owner has explicitly
     authorised that workflow for the task.

3. **Running Checks Locally:**
   Before creating a pull request, run the validation suite. It builds both
   platforms, runs the Swift unit tests, and runs the push gateway tests and
   dependency policy. It needs no Chatwoot server, Apple service, credentials,
   or signing identity:
   ```bash
   ./script/ci.sh
   ```

   To include the macOS UI tests, which need an ad-hoc signed test runner:
   ```bash
   ./script/ci.sh --with-ui-tests
   ```

   To build, launch, and verify the Mac app:
   ```bash
   ./script/build_and_run.sh --verify
   ```

4. **Project Changes:**
   `WootDesk.xcodeproj` is generated by XcodeGen from `project.yml`. Make target,
   build setting, and entitlement changes in `project.yml`, run
   `xcodegen generate`, and commit both files. Direct edits to the generated
   project or to `WootDesk/Resources/WootDesk.entitlements` are overwritten.

5. **Code Quality Guidelines:**
   - Adhere to Swift 6 strict concurrency rules.
   - Maintain test coverage for all new API, model, or persistence features.
   - Use British English for all user-facing strings and documentation, and no em or en dashes anywhere.
   - Keep views lightweight by encapsulating complex logic in `@Observable` state objects or actors.

6. **Never Include Real Data:**
   Pull requests must not contain an access token, a real server address, customer
   message content, or personal data, in code, fixtures, tests, documentation,
   screenshots, or CI logs. Use invented values and `example.com` hosts.

7. **Release and Signing Changes:**
   - Keep `CODE_SIGN_STYLE` automatic and do not commit a personal or organisation `DEVELOPMENT_TEAM` value.
   - Follow `docs/APP_STORE_SUBMISSION.md` and update the traceability, risk, and release-readiness records when distribution behaviour changes.
   - A successful build or archive is evidence, not approval to upload, invite testers, submit for review, or publish.

## Code of Conduct

Please note that this project is governed by the [Code of Conduct](CODE_OF_CONDUCT.md). By participating, you agree to uphold its standards.

## Security Reports

Do not include vulnerabilities, credentials, customer data, or private server
details in a public issue. Follow [SECURITY.md](SECURITY.md) and use GitHub's
private vulnerability reporting flow.
